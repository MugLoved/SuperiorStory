Superior Story is a JSON authoring system for conversations, scenes, and quests. Its purpose is a highly performant, robust, flexible, and easy-to-use questing and conversation mod whose content is written in datapack JSON with as little authoring as possible.

For the current bundled quest inventory, tasks, dialogue choices, prerequisites, and rewards, read [Quest Catalog](docs/reference/QUEST_CATALOG.md). Quest JSON and runtime remain authoritative for behavior.

## Modular JSON Authoring Contract (binding)

- Everything must be modular. Every piece of behavior (speakers, triggers, conditions, actions, line kinds such as `locate`, item hand-over, objectives, rewards, structure pools, derived variables) is a self-contained module registered through one Story registry and composed by JSON. Adding a new module or a new kind of piece must not require rewiring the dialogue engine, session lifecycle, loaders, packets, or existing modules. A feature that only works for one hard-wired case (one trigger, one speaker type, one quest shape) is incomplete.
- Every module must be usable from JSON. A capability that exists only in Java, or only through another module's special case, is incomplete. Other mods extend Story by registering modules through the public `api` package, never by editing Story.
- Modules plug in wherever their kind is accepted. A condition works in dialogue, line, and choice `if`/`unless`; an action works on choices, accepted inputs, triggers, and objective completion; a speaker works with every line kind. Do not add per-location copies.
- Minimal authoring by default, full control when wanted. Every field except the few that identify the content has a default. The smallest useful file stays one or two lines. Authors who want high customization can specify every field explicitly. Do not add required fields.
- Derive instead of author. IDs come from file paths, ordering from array order, choice IDs from their position, quest stages from their objectives, pools from profile files, dimensions from structure placements, speaker names and portraits from the entity or block, quest entities from profile bosses, and display names from registries. Only ask authors for information that cannot be derived; an explicit field may always override a derived value.
- Validate at load. Modules parse and compile their JSON once on reload, reject unknown keys with the file and field named, and keep valid content active when a sibling is invalid. Runtime never re-parses JSON.
- Stay performant. Selection and condition checks run on already compiled data; structure searches go through the narrowest pool or the recorded structure index, never an unbounded search by default. General (all-structure) location happens only where content explicitly asks for it.
- All player-facing text Story adds lives in `assets/superiorstory/lang/en_us.json` (or a translation key authored in JSON) so it can be translated; no player-facing literals in code.
- Reputation is bounded to -10 (minimum) through 10 (maximum) inclusive. This is binding for every agent and every feature. `ExtraModules.REP_MIN` / `REP_MAX` are the only definition; `addReputation` (the one writer) clamps the total, `reputation` clamps on read, and the `rep` condition rejects out-of-range `min`/`max` at load. Never author, document, test, or hard-code a reputation threshold above 10 or below -10, never add a second reputation store, and never widen the range without an explicit operator instruction. Bountiful's -30 to 30 scale is reached only through the fixed factor of 3 in `BountifulBridge` (uncommon at 2, rare at 5, epic at 9, legendary at 10).
- Dialogue variety is authored with line pools and word pools (`line_pools/`, `word_pools/`, the `pool` line form and the `{~word}` token), rerolled on every conversation, entries gated by the ordinary `if`/`unless` conditions. Follow `docs/plans/SUPERIOR_STORY_DIALOGUE_POOLS_PLAN_2026-09-30.md`; prefer adding an entry to an existing pool over duplicating a line across dialogues.
- Quest rewards and dialogue choices give per-player unlock keys through the core `unlock` / `lock` actions and `unlocked` condition (`module/CoreModules.java`, value grammar in `dialogue/UnlockSpec.java`). Superior Lib owns the key store (`PlayerUnlockApi`, change event, client sync, `/superior_lib unlock|lock|unlocks`); Superior Shop owns its gates and key vocabulary (`category:<id>` / `entry:<id>`, see `/home/alexh/superior-linux/addons/superior_shop/docs/plans/SHOP_QUEST_UNLOCKS_PLAN_2026-09-30.md`), and Lib recipe locks read the same keys. Story never keeps its own copy. Summoning Rituals rituals unlock the same way: Lib recipe locks name a ritual by recipe ID, Lib's `compat/summoningrituals` gates the altar, and Lib's JEI and EMI plugins hide locked recipes; Story adds no code for it (README, "Rituals"). `coins` stays in `compat/shop`.
- When the JSON surface changes, update `README.md` in the same commit.
- The active implementation plan for this contract and the September 29 feature set is `docs/plans/SUPERIOR_STORY_MODULAR_AUTHORING_PLAN_2026-09-29.md`.
- NPC bounty givers over Bountiful (`compat/bountiful`, reputation-gated bounty tiers, Extra Bounties rarity patch data, board removal) follow `docs/plans/SUPERIOR_STORY_BOUNTIFUL_NPC_BOUNTIES_PLAN_2026-09-29.md`. Extra Bounties classification follows [the rarity ruleset](docs/reference/EXTRA_BOUNTIES_RARITY_RULESET.md). Bountiful owns bounty generation, tracking, expiry, and payout; Story owns the conversation, offer store, giver link, and tier gate.
- The fisherman guide (fish fetch quests over Starcatcher, `compat/fishing`, the `profession` condition, quest `location` modules replacing the quest `structure` field, unlock keys in Superior Lib shared by Shop stock and Lib recipe locks) follows `docs/plans/SUPERIOR_STORY_FISHERMAN_PROGRESSION_PLAN_2026-09-30.md`. The guide stays separate from Bountiful: its own files, quest-chain progress, never the bounty reputation. Tide gear retirement belongs to Superior Tweaks, named in that plan.

## Ownership And Integration

- Read the shared workspace `AGENTS.md` and `DOC_MAP.md` before Story work.
- Story owns first-join eligibility, datapack scene loading, authored beats, player-facing screen, one first-join seen flag, and bounded session lifecycle. The hardcoded intro is a separate scene and remains the default first join until a datapack scene declares `trigger: first_join`.
- Superior Respawn owns invulnerability. Story requests and releases its scene protection source; Story must not cancel damage or track a second protection map.
- Superior Sounds owns all scene playback and music scheduling. Story may contribute sound events, assets, catalog rules, and scene state signals; it must not play sounds directly, mix global volume, or integrate Biome Beats.
- Superior Skill Tree and Puffish Skills own their screens. Story selects the installed target and invokes its opening boundary through one handoff flow.
- Preserve the hardcoded five-beat experience and replay/reset commands unless the operator changes their intended behavior. Manual `/superiorstory play <id>` must not mark the first-join intro as seen.
- Story owns dialogue: JSON dialogues (any scene file with a speaker, a structure binding, or a trigger), the Talk key, the speaker hold and facing (NoAI for an NPC, restored on every exit path), the dialogue screen, and the `api` package events (`DialogueChoiceEvent` for every choice, `DialogueEndEvent` once per conversation, `StoryQuestEvent` per quest stage). Other mods subscribe to those events or register modules through `StoryHooks`; they do not edit Story.
- NPC markers (`server/StoryMarkers`, `client/StoryMarkersClient`): the server computes, per player, a "?" (the mob has a dialogue for the player) or "!" (an action's `progresses` says talking would advance a quest) once a second and sends the map when it changes; the client only draws it. New quest verbs opt into the "!" by overriding `StoryHooks.Action.progresses`.
- Superior HUD owns hiding the HUD. Story only calls `presentationHolds()` while a dialogue is open, and only when Superior HUD is installed. The FTB Quests keys (`ftb_quest`, `ftb_task`, and the `ftb_quest` condition) live in `compat/ftbquests`, and the Superior Shop `coins` action in `compat/shop`; each loads only when its mod is present.
- Structure quests: Superior Locator owns the search (Story requests an `ANY`-mode structure search with the silent attribute and only polls it); Superior Skylines owns the waypoint store (Story calls its public `addNamed` / `removeAt` on the client, only when installed, and only after the player accepts and reaches the structure). Story owns the profiles, pools, variables, dedicated structure dialogues, quest files and quest state, the quest drop loot modifier, and `StoryQuestEvent`. Superior Locator owns the known-structure index store (Superior Lib owns its `KnownStructureStartsApi` contract; Superior Worldgen V2 and real chunk loading feed it); Story only queries it. Superior Lib owns boss tier colors; Superior Tooltips owns item and entity tooltip rendering. Extra quest objectives (`also`) live in `QuestObjectives` and are stored inside the quest instance tag; delivery NPCs are temporary, tagged, and never saved (`superiorstory_temp_npc`). Never hard-code structure IDs in code; content belongs in `data/superiorstory/superiorstory/` (`structures`, `pools`, `quests`, `scenes`).
- New bundled mod support is data only: add a profile file for the mod's structures and bosses, and validate every ID against the installed jar.
